# مقارنة: technicalproposal.com مقابل نظامنا (Smart Pre-Sales Assistant)

تاريخ التحليل: 2026-07-30
النظام محل المقارنة: `presales_codex_ready/imdad` — تطبيق Streamlit (1761 سطر) يعتمد على Google Gemini.

---

## 1. الخلاصة التنفيذية

نظامنا يغطي بشكل معقول **قلب العملية**: رفع الكراسة → تحليل ذكي → بناء أقسام العرض → تصدير Word.
لكنه يغطي تقريباً **40٪** مما يعرضه الموقع المرجعي.

الفجوات الكبرى مرتّبة حسب الأثر:

| # | الفجوة | الأثر |
|---|--------|-------|
| 1 | لا يوجد **تكامل مع منصة اعتماد** — كل شيء يدوي (رفع ملفات) | عالٍ |
| 2 | لا يوجد **ذكاء سوقي**: تحليل المنافسين، العروض السابقة، حركة الأسعار | عالٍ |
| 3 | لا توجد **مرحلة مراجعة** (فنية/تجارية/قانونية) قبل التسليم | عالٍ |
| 4 | **هيكل العرض ثابت** (9 أقسام مثبّتة في الكود) وليس مُقترحاً حسب طبيعة المنافسة | عالٍ |
| 5 | **اقتطاع السياق إلى 20,000 حرف** — يفقد معظم محتوى الكراسة الحقيقية | حرج تقنياً |
| 6 | لا يوجد **تصدير PDF**، ولا دعم **إنجليزي/ثنائي اللغة** | متوسط |
| 7 | **لا يوجد حفظ دائم** — كل شيء في `session_state` ويضيع بإغلاق المتصفح | متوسط |
| 8 | لا يوجد **استخراج تلقائي** لجدول الامتثال وجدول الكميات (تُملأ يدوياً) | متوسط |

## 3. نقاط قوة نظامنا (لا يعرضها الموقع المرجعي)

1. **حقن القالب الرسمي للشركة** — رفع `.docx` بترويسة الشركة والحقن داخله (`company.py:78`).
2. **حلقة الإنسان في المسار (Human-in-the-loop)** — كل تحليل له حقل "ملخص معتمد" يحرّره المهندس، ويُمرَّر لاحقاً لتوليد المنهجية (`ui.py:61`، `doc_builder.py:117-121`). تصميم ذكي يمنع تراكم أخطاء الـ AI.
3. **تصدير/استيراد مساحة العمل JSON** مع استبعاد مفاتيح API (`settings.py:76-87`).
4. **تشغيل محلي بالكامل** — مفاتيح API في الذاكرة فقط، لا سحابة، مناسب للبيانات الحساسة.
5. **جداول امتثال وBOQ قابلة للتحرير** مع تصدير CSV.

## 5. خارطة طريق مقترحة

### المرحلة أ — إصلاحات أساسية (أيام)
1. إعادة تسمية `pages/` → `views/`.
2. تحديث نماذج Gemini إلى الجيل الحالي.
3. رفع حد السياق من 20 ألف حرف إلى الحد الكامل للنموذج (السياق الطويل متاح الآن)، مع تقسيم ذكي (chunking) للكراسات الضخمة.
4. استبدال `PyPDF2` بـ `pypdf` + إضافة OCR للملفات الممسوحة.

### المرحلة ب — إغلاق الفجوات عالية الأثر (أسابيع)
5. **مرحلة المراجعة ثلاثية الزوايا**: ثلاثة prompts (فني/تجاري/قانوني) تنتج ملاحظات مُهيكلة + زر "طبّق التحسين" يستبدل نص القسم.
6. **استخراج مُهيكل**: جعل الـ AI يُرجع JSON بدل Markdown، ليملأ جدول الامتثال وBOQ تلقائياً بدل الإدخال اليدوي.
7. **هيكل عرض ديناميكي**: خطوة يقترح فيها النظام الأقسام حسب طبيعة المنافسة قبل الصياغة.
8. **تصدير PDF** + فهرس محتويات وترقيم صفحات.

### المرحلة ج — التمايز (أشهر)
9. **حفظ دائم ومفهوم "مشروع/منافسة"** — قاعدة بيانات (SQLite كافية) بدل `session_state`.
10. **مستودع معرفة فعلي (RAG)** — السير الذاتية والشهادات والمشاريع السابقة تُغذّى فعلياً للـ AI (حالياً حقول رفع معطّلة في `company.py:97`).
11. **تكامل اعتماد** — إن توفّر وصول رسمي عبر API. هذه أكبر فجوة وأصعبها.
12. **دعم ثنائي اللغة** — تحويل الـ prompts لمَعلمة لغة بدل التثبيت على العربية.

## 6. قرار استراتيجي

النظام لن يجاري الموقع المرجعي في **بيانات السوق وتكامل اعتماد** بدون وصول رسمي لتلك البيانات، وهذا خارج نطاق التطوير البرمجي وحده.

التمايز الواقعي لنظامنا:
- **الخصوصية والتشغيل المحلي** — بيانات العطاءات لا تغادر جهاز الشركة.
- **حقن قالب الشركة الرسمي** — مخرَج جاهز بهوية الشركة، وليس مستنداً عاماً.
- **مستودع معرفة خاص بالشركة** — عرض مبني على مشاريع الشركة وسيرها الذاتية الحقيقية، لا محتوى عام.

المرحلتان (أ) و(ب) تُوصلان النظام لمستوى تنافسي في جوهر المنتج — إعداد العرض الفني — دون الحاجة لطبقة البيانات السوقية.
